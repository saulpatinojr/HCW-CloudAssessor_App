## 5 Architectural issues

1. **No deliverable, no stack (R-001, T-001).** Everything downstream was blocked on a decision the owner has now made. The plan makes the decision concrete rather than re-opening it.
2. **Engine ownership is inverted at the start.** The AddOn writes the engine first because this repository is empty, which is the opposite of ADR-0028's model. Left alone, two engines with one name would drift (risk CA-RK-3). The adoption step in section 15 closes the inversion within one release.
3. **Three permission planes, one identity.** ARM reads (`Reader`), cost (`Cost Management Reader`) and directory reads (Microsoft Graph) are separate grants (`TODO.md` T-011 note). The appliance takes the first two on one user-assigned identity; Graph is deferred, so the identity-posture criteria stay `unknown` in the appliance as they do in the lab.
4. **The same pane for two editions.** The appliance serves the AddOn's pane UI, which expects an upload route. The appliance removes the upload path and the UI must render the "current assessment" mode from `/api/health` without a code fork (section 7.9).
5. **Scale-to-zero versus an in-memory snapshot.** A Consumption app that scales to zero loses the cached assessment and the first visitor waits for a cold collection. `min_replicas 1` is the default; the trade is documented, not chosen silently.
6. **Governance versus documentation volume.** The four-file model has no destination for ADRs, runbooks or an API contract while the wiki is not writable (R-007). The wiki workaround in the header block is the only sanctioned path; nothing in this plan creates `docs/`.
7. **A permanently red check (R-008).** `qlty check` cannot be a required status until the Cloud-side fault is read. Branch protection (T-006) is sequenced after it, not around it.

```python
FORBIDDEN_ENV = ("AZURE_CLIENT_SECRET", "AZURE_CLIENT_CERTIFICATE_PATH", "AZURE_USERNAME", "AZURE_PASSWORD", "AZURE_TENANT_ID")
# AZURE_TENANT_ID is refused on purpose: ManagedIdentityCredential needs only the client id, and a tenant id in the
# environment is the signature of a service-principal login. Section 10 states the same rule.
def build_credential(env: Mapping[str, str]) -> TokenCredential:
```

### 7.5 `src/cloud_assessor_appliance/collectors/scope.py`

- **Current behavior:** absent (T-027 scope half).
- **Required behavior:** a parsed allow-list of `/subscriptions/<guid>` and `/subscriptions/<guid>/resourceGroups/<name>` entries from `CA_SCOPES` (comma or space separated), enforced before any query; anything outside raises `ScopeError`; no management-group traversal in v1.
- **Exact code-level change:**

```python
@dataclass(frozen=True)
class Scope: subscription_id: str; resource_group: str | None
class ScopeAllowlist:
    @classmethod
    def parse(cls, value: str) -> "ScopeAllowlist": ...   # parses the raw value, e.g. "/subscriptions/<guid>,/subscriptions/<guid>/resourceGroups/rg-app"
    @classmethod
    def from_env(cls, env: Mapping[str, str]) -> "ScopeAllowlist":
        return cls.parse(env.get("CA_SCOPES", ""))        # the only place the key name CA_SCOPES is spelled
    def subscriptions(self) -> list[str]
    def kql_filter(self) -> str   # "subscriptionId in ('...')" plus per-RG "resourceGroup =~ '...'" clauses
    def assert_contains(self, resource_id: str) -> None   # ScopeError otherwise
```

- **Tests:** `tests/unit/test_scope.py`: parse both shapes, reject malformed, `kql_filter` output pinned, `assert_contains` rejects a foreign subscription.
- **Acceptance criteria:** every collector calls `assert_contains` or `kql_filter`; a test monkeypatches the ARG client and proves no query runs with an empty allow-list.
- **Priority:** P1. **Dependencies:** none. **Rollback:** module deletion.

## 16 Compatibility considerations

- **Four-file governance.** This file is the fifth root file until the first release moves it to the wiki `Implementation-Plan` page; `scripts/check-docs-governance.py` allow-lists it by name so the model is enforced, not merely stated.
- **AddOn compatibility is by exact tag pin.** The AddOn never floats on `main`; `core-update.yml` tests each release before adopting it and labels the PR `compatible` or `needs-adaptation`. A core change that breaks the lab is caught in the AddOn's CI, not on the lab host.
- **Model version field.** `MODEL_VERSION = 1` in every `Resource`, `Assessment` and `report.json`; the catalog `version` beside it. Evaluator kinds are only added (`cost-evidence` is the first addition); ids are never reused; a changed criterion bumps its own `version`.
- **One pane, two editions.** The pane branches on `edition` from `/api/health`; no field the lab relies on is removed. The health envelope stays flat and carries the standard's fields; the appliance adds `scope` and `lastRun` as extras the website proxy would ignore if it ever read them (it does not; the appliance is never framed by the site).
- **Python line.** `requires-python = ">=3.14.6,<3.15"` in both packages (floor 3.14.6, image 3.14.7, no 3.15 until the floor test says so); the AddOn shares the range and the base image digest, so one `versions.env` bump lands in both repositories through their own PRs.
- **Terraform pattern parity.** The root mirrors the AzMigrate appliance root's naming and provider constraints so an operator who knows one can read the other.
